# inyeqai — TCP поверх WebSocket на Java + Spring Boot

Самодостаточная замена связки **chisel-клиент ⇄ chisel-сервер** из схемы цепочки: вход
в туннель на `127.0.0.1:3128`, транспорт по `wss`, публичный сервер. Один jar, два режима
(`server` / `client`), как у chisel.

```
claude.exe / agent-desk ──HTTPS_PROXY──▶ client 127.0.0.1:3128 ──wss──▶ server (публичный)
                                           (вход в туннель)                  │
                                                                              ▼
                                                         dial host:port, выход в сеть
```

Это **функциональный** аналог `jpillora/chisel`, не совместимый с ним по проводу: у chisel
внутри WebSocket идёт SSH, здесь — свой простой протокол мультиплексирования TCP. Поэтому
java-клиент работает только с java-сервером и наоборот.

Если сеть не пропускает WebSocket, тот же туннель работает поверх обычного HTTP — см.
[Если WebSocket не проходит](#если-websocket-не-проходит). Клиент выбирает транспорт сам.

Лимит «≤ 500 КБ» на схеме — это ограничение squid (`REQUEST_BODY_MAX`) дальше по цепочке,
не самого туннеля. CONNECT-туннель для squid непрозрачен, поэтому к `wss` он не применяется;
при необходимости такой лимит добавляется на входе отдельно.

## Сборка

Нужен JDK 17+ (проверено на 21) и Maven. В корпоративной сети зависимости тянутся из
Nexus; дома, если артефакты уже в `~/.m2`, собирать офлайн:

```bash
mvn -o package        # сборка + тесты
mvn -o package -DskipTests
```

Результат — `target/inyeqai.jar` (исполняемый fat-jar).

## Запуск

Сервер (публичная сторона):

```bash
java -jar inyeqai.jar server --port 8080 --auth tunnel:СЕКРЕТ
```

Клиент (вход в туннель), пробросы в синтаксисе chisel:

```bash
java -jar inyeqai.jar client --auth tunnel:СЕКРЕТ --keepalive 25s \
    wss://ПУБЛИЧНЫЙ-АДРЕС/ \
    0.0.0.0:3128:127.0.0.1:3129 \
    R:3130:host.docker.internal:3129
```

Это ровно те два проброса, что задаёт `compose.cloud.yaml` для chisel-клиента:

| Проброс | Тип | Что делает |
|---|---|---|
| `0.0.0.0:3128:127.0.0.1:3129` | прямой | клиент слушает `0.0.0.0:3128`, сервер дозванивается до `127.0.0.1:3129` у себя |
| `R:3130:host.docker.internal:3129` | обратный | сервер слушает `:3130`, клиент дозванивается до `host.docker.internal:3129` у себя |

Синтаксис проброса: `[bind:]порт:хост:порт`, с префиксом `R:` — обратный. Без `bind`
прямой слушает `127.0.0.1`, обратный — `0.0.0.0`. Короткие формы достраиваются с конца,
как у chisel: `3000` это `3000:127.0.0.1:3000`, а `example.com:3000` —
`3000:example.com:3000`. IPv6 пишется в скобках: `[::1]:3128:[fe80::1]:3129`.

URL можно давать как `wss://host/`, `https://host` или просто `host` — схема приводится к
`ws/wss`, а если пути нет, добавляется `/tunnel` (эндпойнт по умолчанию).

### Настройки сервера

| Флаг | Назначение | По умолчанию |
|---|---|---|
| `--port` | порт HTTP/WebSocket | `8080` |
| `--host` | адрес прослушивания | все интерфейсы |
| `--auth` | общий секрет; клиент шлёт его в заголовке `X-Tunnel-Auth` | пусто = без проверки |
| `--path` | путь WebSocket-эндпойнта; запасной HTTP живёт под ним (`{path}/http/…`) | `/tunnel` |
| `--allow` | куда клиентам можно; регулярка, флаг повторяется | пусто = куда угодно |
| `--keepalive` | как часто пинговать клиентов | `25s` |
| `--pong-timeout` | молчание, после которого сессия считается мёртвой | `75s` |
| `--no-http-fallback` | убрать запасной транспорт, оставить только WebSocket | запасной включён |

Клиент понимает `-v` / `--verbose` — тогда в лог идёт по строке на каждый поток: куда пошёл,
сколько жил, сколько байт унёс в каждую сторону.

### Проверка живости клиента

У клиента есть свой эндпойнт, `--health [bind:]порт` (по умолчанию слушает loopback):

```bash
java -jar inyeqai.jar client --auth tunnel:СЕКРЕТ --health 9000 wss://host/ 3128:127.0.0.1:3129
```

```
GET /healthz   200 пока туннель рабочий, 503 когда нет
GET /status    тот же вердикт с числами, которыми он получен
```

Он отвечает **про туннель, а не про процесс**. Это разные вещи: клиент, у которого дальняя
сторона пропала без TCP-close, продолжает работать и продолжает принимать соединения, которые
уже не может провести. Обычная проверка живости такое не ловит — она видит живой процесс.
Доказательством служит возраст последнего pong: если они приходят, сервер реально отвечает.

| Ответ | Код | Что значит |
|---|---|---|
| `up` | 200 | соединение есть, сервер отвечает на keepalive |
| `unknown` | 200 | соединение есть, но `--keepalive 0s` — проверять нечем, и это сказано прямо |
| `stale` | 503 | соединение есть, сервер перестал отвечать; вот-вот будет разрыв |
| `down` | 503 | соединения нет, идёт переподключение |

`unknown` отвечает 200 намеренно: называть туннель здоровым без доказательств неправильно, но
и объявлять его сломанным из-за выключенной самим оператором проверки — тоже.

Для контейнера есть режим `healthcheck`: он дёргает такой эндпойнт и ставит код возврата.
Нужен потому, что в образе нет ни `curl`, ни `wget`, а ставить пакет ради запроса на локальный
порт — плохой размен. Запускает JVM на каждую проверку, так что интервал берите щедрый:

```bash
java -jar inyeqai.jar healthcheck http://127.0.0.1:9000/healthz
```

Те же значения читаются из `application.yml` / переменных окружения (`SERVER_PORT`,
`TUNNEL_AUTH`, `TUNNEL_PATH`, `TUNNEL_ALLOW_0`, …). Проверка живости: `GET /healthz` → `ok`.

**Токен только пускает в туннель, он не ограничивает, куда из него можно пойти.** Без
`--allow` клиент с верным токеном дозванивается до любого адреса, видимого серверу, —
включая `169.254.169.254` и всё, что слушает на его localhost. Для цепочки это два правила:

```bash
java -jar inyeqai.jar server --port 8080 --auth tunnel:СЕКРЕТ \
    --allow '^127\.0\.0\.1:3129$' \
    --allow '^R:0\.0\.0\.0:3130$'
```

Регулярки сверяются с `host:port` для прямых потоков и с `R:bind:port` для обратных
слушателей (как адреса в `--authfile` у chisel). Они не заякорены сами собой — пишите
`^…$`, иначе `127\.0\.0\.1:3129` совпадёт и с `127.0.0.1:31299`.

**Пустой `--auth` открывает вход в сеть за сервером — на публичном адресе всегда задавайте
секрет.** TLS (`wss`) обычно терминирует шлюз перед сервером (в цепочке это alfa); если
выставляете сервер наружу напрямую, включите `server.ssl.*`.

### Если WebSocket не проходит

Сервер отдаёт туннель двумя способами сразу: обычным WebSocket на `--path` и запасным — на
простом HTTP под тем же путём (`/tunnel/http/...`). Клиенту отдельный URL не нужен, он сам
выводит адрес запасных эндпойнтов из того же `wss://…`.

```bash
java -jar inyeqai.jar client --auth tunnel:СЕКРЕТ --transport auto wss://host/ 3128:127.0.0.1:3129
```

| `--transport` | Что делает |
|---|---|
| `auto` (по умолчанию) | сначала WebSocket; если попытка не продержалась, следующая идёт по HTTP, и так по очереди |
| `ws` | только WebSocket, без подмен |
| `http` | сразу HTTP, не пробуя WebSocket |

`auto` переключается не по коду ошибки, а по тому, прожило ли соединение хотя бы пять секунд.
Это ловит оба случая: и прокси, который отвечает на `Upgrade` ошибкой, и прокси, который
рукопожатие пропускает, а кадры потом съедает. Транспорт, который продержался, остаётся
выбранным — пока не отвалится снова. В логе переключение видно строкой
`trying the http transport`, а в выводе `/status` у клиента — строкой `transport:`. На сервере
такие сессии помечены id с префиксом `http-`.

Внутри всё устроено так: вниз (от сервера) — один долгоживущий `GET`, в нём кадры идут с
префиксом `[номер:8][длина:4]`, потому что у HTTP-тела нет границ сообщений, а номер нужен, чтобы
оборванный ответ можно было продолжить с нужного места. Вверх — короткие `POST` пачками до
256 КБ, каждая со своим номером. Асимметрия намеренная: поток в теле запроса сломался бы о
прокси, который сначала буферизует тело целиком, и о лимит на размер тела — тот самый squid с
`REQUEST_BODY_MAX` 500 КБ дальше по цепочке. Короткие `POST` проходят и там.

Keepalive здесь — не ping WebSocket, а служебные кадры `PING`/`PONG`, которые обе стороны
обрабатывают внутри транспорта. Поэтому «последний pong» на `/status` и вердикт `stale`
значат ровно то же, что и на WebSocket, а не «проверка недоступна».

#### Обрыв ответа не рвёт туннель

Прокси с лимитом на размер или длительность ответа будет обрывать долгий `GET` регулярно — это
не поломка, а его работа. Поэтому сессия обрыв переживает: клиент приходит снова и просит
продолжить с того кадра, который получил последним, а сервер досылает всё, что было после.
Потоки внутри туннеля этого не замечают — обрыв стоит один round trip вместо пересборки туннеля
с потерей всех соединений.

Чтобы это было восстановлением, а не его видимостью, нужны три вещи:

- **Нумерация кадров вниз.** Кадр мог быть записан в уже мёртвый ответ, и сама запись об этом не
  скажет: «отправлено» тут не значит «доставлено». Поэтому сервер держит кадр, пока клиент не
  подтвердит его кадром `ACK`, и при продолжении переотправляет всё неподтверждённое. Без этого
  буфера восстановленная сессия тихо пропускала бы такие кадры — для потока байт это порча,
  которую не обнаружит ни одна сторона.
- **Номер пачки вверх.** Упавший `POST` не говорит, применил его сервер или нет. Повтор с тем же
  номером сервер подтверждает, но не применяет; пропуск номера значит, что кадры потерялись, и
  тогда сессия закрывается, а не продолжается с дырой.
- **Строгий порядок на приёме.** Клиент принимает только следующий по номеру кадр. Пропуск или
  повтор — фатальная ошибка, а не повод «склеить как-нибудь»: выше этого слоя такое уже не
  отличить от обычных данных.

Границы честные. Буфер неподтверждённого — 2 МБ на сессию, и когда он полон, сервер перестаёт
писать, а не растёт. Пока ответ не прицеплен, кадры копятся в очереди сессии (256 кадров):
нагруженный туннель переживёт короткий обрыв, а не любой — удержать неограниченный объём для
отсутствующего клиента нельзя в принципе. Клиент пробует продолжить 30 секунд, после чего
пересобирает туннель; а если сервер ответил 404 или 410 («нет такой сессии», «с этого места
продолжить нельзя»), он не ждёт и пересобирает сразу.

В `/status` на сервере видно и число восстановлений, и сколько байт держится неподтверждёнными:

```
  carrier resumed 12 time(s), holding 48.0 KB unconfirmed
```

Строка появляется только у HTTP-сессий. Именно она отличает туннель, который работает, от
туннеля, который работает, переприцепляясь каждые две секунды, — снаружи это одно и то же.

Что осталось за рамками: каждая живая HTTP-сессия держит поток в пуле `tunnel-down-` (максимум
200), и это же предел числа одновременных клиентов на этом транспорте.

Запасной транспорт проверяет тот же токен, что и WebSocket, и ходит через тот же `--allow`:
это один и тот же обработчик сессий, разница только в том, чем кадры довезли. Если он не нужен
— `--no-http-fallback` убирает эндпойнты совсем, а не просто прячет.

### Что происходит прямо сейчас

`GET /healthz` отвечает `ok`, а `GET /status` показывает живое состояние — под тем же
токеном, потому что в выводе внутренние адреса и объёмы трафика:

```bash
curl -H "X-Tunnel-Auth: tunnel:СЕКРЕТ" http://127.0.0.1:8080/status
```

```
tunnel server, up 25.1s
sessions 1, streams open 1, carried 3
to clients 293.4 KB, from clients 293.3 KB
allow list: 2 pattern(s)

session 078460e9-cb11-12c1-2ce9-6bde683e1216 from /127.0.0.1:54481
  up 12.8s, last pong 89ms ago
  reverse listeners: [18130]
  streams open 1, carried 3, sent 293.4 KB, received 293.3 KB
    2          127.0.0.1:18090              open     3.1s  sent 193 B      received 37 B
```

Самое полезное тут — `last pong`: он отличает сессию живую от всего лишь подключённой.
Отключить эндпойнт целиком: `tunnel.status: false`.

Id потока печатается беззнаковым. Сервер помечает свои id старшим битом, поэтому как `int`
они отрицательные; беззнаковый вид даёт на обеих сторонах туннеля один и тот же токен, по
которому логи клиента и сервера сопоставляются вручную.

## Как это устроено

- **Протокол** (`common/Frames.java`): одно бинарное WebSocket-сообщение = один кадр.
  `OPEN` (открыть поток на host:port), `DATA` (байты потока), `CLOSE`, `CONFIG` (клиент
  просит сервер поднять обратные слушатели), `EOF` (сторона закончила писать), `WINDOW`
  (получатель отдал кредит). Старший бит `streamId` помечает инициатора, чтобы id двух
  сторон не пересекались. Ещё три кадра — `PING`, `PONG`, `BYE` — принадлежат не туннелю, а
  транспорту: их видит только HTTP-транспорт, у которого нет своих ping/pong/close, и обе
  стороны обрабатывают их у себя, не пропуская в мультиплексор.
- **Half-close**: `EOF` повторяет полузакрытие TCP — сторона перестаёт писать, но
  продолжает читать. Без него `CLOSE` рвал оба направления сразу, и запрос по схеме
  «отправил, закрыл запись, жду ответ» не получал ответа никогда.
- **Обратное давление**: на каждое направление каждого потока есть окно в 256 КБ
  неподтверждённых байт, получатель возвращает кредит по мере записи в сокет. Иначе быстрый
  локальный читатель при медленном туннеле раздувал бы очередь без границы.
- **Мультиплексор** (`common/Mux.java`): общий для обеих сторон. Путь разбора кадров
  никогда не блокируется на сокете: диал и запись живут в отдельных потоках на поток. Один
  недоступный хост или один залипший получатель больше не вешает весь туннель.
- **Сервер** (`server/`): Spring WebSocket-эндпойнт, по сессии — свой `Mux` и обратные
  слушатели; отправка в сессию сериализована (её нельзя писать из нескольких потоков).
  Токен проверяется на рукопожатии (`AuthHandshakeInterceptor`), иначе 401; куда можно
  дозваниваться — `AddressPolicy`. Сервер сам пингует клиентов и закрывает замолчавшие
  сессии: иначе клиент, пропавший без TCP-close, навсегда держал бы свои обратные порты.
- **Клиент** (`client/`): JDK `java.net.http.WebSocket`, без лишних зависимостей. Очередь
  отправки сериализует вызовы, keepalive не только пингует, но и **следит за ответами** —
  туннель без pong рвётся и переподключается с нарастающей задержкой (1с → 5мин).
- **Два транспорта, один код сессии.** Запасной HTTP-транспорт не дублирует логику сессий, а
  подставляет себя на место WebSocket: на сервере `HttpCarrierSession` реализует
  `WebSocketSession`, и `HttpTunnelController` дёргает те же колбэки обработчика, что дёрнул бы
  контейнер; на клиенте `HttpLink` реализует `WebSocket`, и `ClientConnection` не знает, что
  под ним. Поэтому обратные слушатели, `--allow`, отстрел замолчавших сессий, `/status` и
  вердикты health одинаковы на обоих транспортах по построению, а не по договорённости — второй
  реализации, которая могла бы разъехаться с первой, просто нет.
- **Сессия живёт дольше своего ответа** (только HTTP). Долгий `GET` — вещь, которую прокси рвёт
  по своим причинам; сессия — нет. Когда ответ заканчивается, сервер освобождает слот и ждёт,
  что клиент придёт продолжить, а решает судьбу сессии по-прежнему только keepalive-жнец,
  который спрашивает, отвечает ли ещё *клиент*, а не открыт ли конкретный ответ.

## Чего нет

SOCKS5 (`socks`, `R:socks`), UDP (`/udp`) и `stdio:`-пробросы не реализованы — в цепочке они
не нужны. Парсер их не примет, а не сделает вид, что понял.

## Тесты

```bash
mvn -o test
```

Интеграционные тесты поднимают настоящий Spring-сервер на случайном порту и гоняют против
него реальный клиент. Первые четыре прогоняются по **обоим транспортам** (`@EnumSource`):
запасной путь либо проходит ту же планку, что WebSocket, либо тест красный. Отдельной копии
набора для HTTP нет намеренно — она разъехалась бы с оригиналом при первой же правке.

| Тест | Что проверяет |
|---|---|
| `TunnelEndToEndTest` | байты проходят прямым и обратным пробросом; half-close доносит EOF до адресата, и тот ещё может ответить; 4 МБ проходят через окно flow control без потерь и перестановок |
| `TunnelKeepaliveTest` | туннель, простоявший дольше обоих pong-таймаутов, остаётся живым (то есть pong реально ходят в обе стороны); `--keepalive 0s` не падает |
| `TunnelStaleSessionTest` | клиент, пропавший **без** TCP-close, не блокирует свой обратный порт навсегда: переподключившийся забирает его обратно |
| `TunnelAllowListTest` | адрес вне `--allow` не дозванивается, обратный слушатель вне `--allow` не поднимается |
| `HttpFallbackTest` | клиент за прокси, который отвечает на `Upgrade` ошибкой, сам доходит до HTTP и везёт байты; с `--transport ws` — не подменяет транспорт, а продолжает падать |
| `HttpResumeTest` | 4 МБ проходят через прокси, который рвёт поток вниз каждые 256 КБ (17 восстановлений за прогон), и возвращаются байт в байт; поток, открытый до обрыва, работает после него |
| `HttpResumeProtocolTest` | повтор пачки подтверждается, но не применяется дважды; пропуск номера пачки закрывает сессию (410); просьба продолжить с кадра, которого не было, закрывает сессию; сессия и её обратный слушатель переживают конец ответа |
| `HttpStaleSessionTest` | замолчавшая HTTP-сессия (кто-то открыл поток вниз и больше не отвечает) теряет свой обратный порт по pong-таймауту |
| `HttpTransportAuthTest` | все три HTTP-эндпойнта требуют токен; без него 401, и `/up` не раскрывает, существует ли сессия |
| `HttpFallbackDisabledTest` | `tunnel.http-fallback=false` убирает эндпойнты (404), `/healthz` продолжает работать |
| `StatusEndpointTest` | `/status` без токена и с неверным токеном — 401; при живом потоке показывает его адрес, счётчики байт и корректную строку потока |
| `StatusDisabledTest` | `tunnel.status=false` убирает эндпойнт (404), `/healthz` продолжает работать |
| `ClientHealthTest` | при живом туннеле — 200 `up`; после разрыва тот же живой процесс отдаёт 503 `down`; с выключенным keepalive — `unknown` с объяснением |

Проверки протокола, разбора аргументов и форматирования — отдельными модульными тестами
(`FramesTest`, `FramingTest`, `ForwardSpecTest`, `TunnelClientTest`, `AddressPolicyTest`,
`SharedSecretTest`, `StreamInfoTest`, `HumanFormatTest`).

`TunnelStaleSessionTest` опирается на `MuteWebSocketClient` — ручной WebSocket-клиент,
который завершает рукопожатие и потом молчит, не отвечая на ping. Так выглядит ноутбук,
ушедший в сон: TCP-соединение со стороны сервера ещё установлено, а отвечать уже некому.
Убить обычный клиент для этого не годится — ОС закрывает его сокеты.

`HttpFallbackTest` так же опирается на `UpgradeBlockingProxy` — прокси, который обычные запросы
пропускает, а на `Upgrade` отвечает 400. Важно, что клиенту никто не сообщает, что именно не
так с сетью: он обязан дойти до этого сам, из неудавшегося рукопожатия к хосту, который во всём
остальном отвечает нормально. Вердикт тест читает с сервера (`/status`), а не из отчёта
клиента, — иначе его устроил бы клиент, которому только кажется, что он переключился.

`HttpResumeTest` опирается на `DownstreamCappingProxy` — прокси, который рвёт поток вниз после
заданного числа байт, а запросы пропускает. Проверка там одна и единственно надёжная: все 4 МБ
обратно, байт в байт. Восстановление, пропустившее кадр или переотправившее лишний, не поднимет
никакой ошибки — оно просто вернёт другие байты. Именно так и был найден баг, когда кадры,
вынутые из очереди, но ещё не попавшие в буфер переотправки, терялись при обрыве записи посреди
пачки: нумерация оставалась непрерывной, а 104 КБ пропадали.
